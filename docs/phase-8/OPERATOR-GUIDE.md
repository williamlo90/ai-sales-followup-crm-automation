# Local V1 operator guide

This release is a **local, connected-sandbox-validated** sales follow-up assistant. The operator owns customer context and the final decision; a separate approver authorizes the exact CRM or email action. A draft is not a sent message. The operator queues a source-backed follow-up; the worker can send an approved email automatically when due. Sending defaults off and requires email_send_enabled=true plus an exact email_recipient_allowlist in ignored local/connectors.json. The new opt-in path has offline regression coverage; it has not been exercised as a new connected send in this UI update. Check /health/ready for the effective send_enabled state before expecting dispatch.

## Install and start

1. From a trusted source checkout, build `local/releases/sales-followup-local-v1.zip` with `python -m scripts.package_release`, then verify it with `python -m scripts.verify_release local/releases/sales-followup-local-v1.zip --extract-to <empty-directory>`. A fresh clone has no ZIP until this build command runs. The manifest hashes every source file; the archive contains example configuration and synthetic fixtures, no credentials or runtime database. Use the extracted directory for all remaining commands. Python 3.13, Node 22, pinned packages in `backend/requirements.lock`, `backend/requirements-postgres.txt`, `web/package-lock.json` and `mcp-server/package-lock.json`, and the digest-pinned PostgreSQL/n8n images in `deploy/compose.yaml` define this candidate. The recorded Phase 8 archive hash identifies the original validated snapshot; a newly built archive after later documentation changes will have a different hash.
2. Create `.venv`, install both Python requirement files, then run `npm ci --prefix web` and `npm ci --prefix mcp-server`. Run `.venv/Scripts/python.exe -m pytest -q`, `npm run build --prefix web`, and `npm run build --prefix mcp-server`. Run `npm run test --prefix mcp-server` for the reference client. On PowerShell, use `npm.cmd` instead of `npm` when script execution policy blocks the shim.
3. Copy `.env.example` to `.env`; set only this project's OpenAI key and accepted model settings when an authorized bounded model run is intended. Copy `deploy/connectors.example.json` to ignored `local/connectors.json`; configure the exact sandbox tenant/deal/worker and project-local token-file paths. Follow [connector setup](../phase-7/CONNECTOR-SETUP.md). Never paste tokens into chat, export them with the ZIP, or borrow credentials from another project. For PostgreSQL, create `local/secrets/postgres_password` and `local/secrets/n8n_encryption_key` locally. Preserve the n8n key with its volume; a different key cannot decrypt existing credentials. Provision a database owner and a separate least-privilege runtime role, migrations, tenant and actors as described in [PostgreSQL runtime](../phase-7/POSTGRES-RUNTIME.md).
4. Keep `crm_write_enabled=false` for preparation. Run `docker compose -f deploy/compose.yaml --profile data --profile engine up -d` only after checking available RAM and other containers; PostgreSQL is capped at 256 MiB, n8n at 512 MiB. The application is native: set `SALES_STORAGE=postgresql`, `SALES_POSTGRES_DSN` (in process environment, never a committed command), `SALES_IDENTITIES_PATH=local/identities.json`, and `SALES_CONNECTORS_PATH=local/connectors.json`; run `.venv/Scripts/python.exe -m uvicorn backend.app:from_environment --factory --host 127.0.0.1 --port 8040`. Start the UI with `npm.cmd run dev --prefix web` on 127.0.0.1:8044. Check `/health/live` and `/health/ready` before exposing work to the operator. Do not run the sandbox as an internet-facing service.
5. Import `automation/n8n/intake-v1.json` and `due-v1.json` while **inactive**. Set their `CONFIGURE_SALES_WORKER` header credential to a scoped worker token in n8n's credential store. Replace the example backend host with the address reachable from the n8n container; verify authentication, tenant mapping and one dry/read-only tick first. The exports are three-minute schedules in `Asia/Jakarta`, with one bounded 90-second wait and at most two tick calls per execution. Activate one copy of each workflow only after checking no prior active copy exists. Capture workflow IDs and activation time in the local handover record. n8n coordinates; the backend owns queue/checkpoint/idempotency.

## Daily use

Open the workspace as the operator, inspect the source quote, matched customer/deal, current CRM context, proposed field diff, next activity and follow-up draft. Resolve ambiguous dates, unsupported claims, stale context and opt-outs before handoff. Record a source-backed commitment through Intake, then queue CRM and email separately in the decision panel. A distinct approver checks the exact version/payload and approves only the intended effect. The operator then checks the operation status and the Odoo read-back; for email, an accepted Graph response or Sent Items observation is **not** delivery/read proof. Keep a human review of the actual recipient, subject and body before an approved send.

`queued` or `awaiting_approval` needs operator/approver work. `review` needs explicit investigation and cannot be silently retried. `unknown` means an external outcome is unresolved: observe the target first, then use the recovery view. `verified` means the target-state observation matched the operation; it does not infer other downstream effects. Use the scoped `/v1/workflows/jobs` list and the UI recovery panel for the owning tenant; do not edit the database ledger by hand.

## Health and incident response

At start and end of an operating session, check `/health/ready`, n8n active workflow count and failed executions, backend jobs in `review`/`unknown`, and the OpenAI budget ledger if model use is enabled. The local `scripts.readiness_monitor` can record readiness transitions and deliver them to a configured loopback receiver; no human notification service is installed by default. The operator must check workflow backlog/unknown outcomes separately. Record incident start/end, affected job/operation IDs, source version, observed target state, action and repeat-check result in an ignored local log. Escalate to the sandbox owner for ambiguous customer identity, missing permission, changed source, or an outcome that cannot be observed.

For expired Graph tokens, refresh the project-local token file, rerun the read-only `scripts.graph_readiness`, then resume the same job; do not create another job. For Odoo/Graph timeout or `unknown`, observe the target using the operation ID first. For a stale source or expired approval, return to human review and create a new approved version. For n8n failure, deactivate its workflow, inspect the failed execution and backend job, repair the cause, then resume one workflow. Do not replay a write request blindly. After a fix, run relevant tests and one scoped read-back before restoring normal scheduling.

## Stop, backup, restore and rollback

Deactivate both n8n workflows first; wait for in-flight executions, then stop the native API/UI. Stop only the project-owned Compose services with `docker compose -f deploy/compose.yaml --profile data --profile engine stop`; do not stop Docker Desktop or other projects. Preserve PostgreSQL and n8n named volumes together with their encryption key, project-local configuration and release ZIP/manifest. Keep secrets in a separate protected backup. Test a restore into a **disposable isolated copy** before relying on the backup. Restore the database and n8n state to a stopped deployment, verify health, workflow count, credential decryption, actor scope and operation read-back, then reactivate one copy of each workflow. Never revert a remote Odoo or Graph effect by restoring the local database; reconcile it by observation and human decision.

Rollback a failed code/workflow change by deactivating schedules, backing up current state, returning to the previous verified release ZIP and its matching workflow exports/config, restoring the previous n8n state if required, running migrations only in the supported direction, and executing regression/read-back checks. The Phase 7 rollback drill restored n8n state and schedules in isolation; it was not atomic rollback of external effects. If a schema migration cannot be reversed safely, keep the service stopped and restore the full matched database backup rather than improvising a downgrade.

A sleeping/offline laptop stops the native API and n8n schedule. On return, check Docker Desktop, the Ubuntu Docker socket if using WSL, PostgreSQL, n8n and `/health/ready`; reattach Docker Desktop's Ubuntu user-distro proxy if the socket is missing, without restarting unrelated containers. Re-enable only one instance of each schedule. The persisted cursor and operation ledger let eligible work catch up, while duplicate enqueues return the same job and unresolved writes require observation. Phase 7 demonstrated missed-interval catch-up in a 10-second lab cadence, one verified Odoo effect, and an unknown Graph ledger reconciled with zero re-sends. This is not proof that a laptop runs while asleep or guarantees every external delivery.

The local owner holds credentials, mailbox consent, sandbox Odoo mappings, backups and support decisions. Model calls consume the existing project budget; Graph Explorer tokens expire and have no unattended refresh. Retain n8n execution history for 72 hours as configured, and review backup/retention needs before real customer use. Hosting and human-facing alerts belong to a separately scoped deployment.
