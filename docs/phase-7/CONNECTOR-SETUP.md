# Project-scoped connector setup

This page explains project-scoped configuration. Connected sandbox acceptance was subsequently completed in [the Phase 7 audit](COMPLETION-AUDIT.md); copying these examples alone does not enable an external write. The release defaults remain off until the operator explicitly configures and approves a scoped action.

Copy deploy/connectors.example.json to ignored local/connectors.json and replace every placeholder with authorized project sandbox mappings. Remove an optional odoo/graph section if it is not selected. Set process variable SALES_CONNECTORS_PATH=local/connectors.json when launching the existing app factory. The local tenant and worker UUID must match the server identity file and PostgreSQL actors; mapped deals must be within that worker's allowed scope. Unknown flags, including send_enabled, are rejected.

- Odoo: connector #2 loopback URL, connector tenant, dedicated sandbox company/opportunity/assignee IDs and token file belonging to this authorized sandbox operator. Reuse its API contract; do not borrow unrelated production credentials or modify its live database.
- To reproduce that dependency from a clean checkout, follow the [pinned project 02 sandbox setup](ODOO-SANDBOX-REPRO.md) before enabling any Sales write.
- Graph: project test mailbox/folder and explicit message-ID-to-local-deal mapping. Choose one authentication method: a short-lived `token_file`, or project-owned Outlook OAuth with `oauth.client_id` and an encrypted cache inside `local/secrets`. Missing/expired credentials fail at the connector boundary.

All configuration/token paths are resolved under this project's local directory. No upward secret discovery. Token files are read afresh per request; neither composition nor startup makes network calls. No credentials should be pasted into chat or committed.

POST /v1/ingest/graph/poll is authenticated, accepts only the exact configured worker+tenant and processes one bounded Graph page atomically. Repeated pages remain idempotent; next-page scheduling belongs to the caller. Odoo connector-preparation/binding endpoints also check the configured local tenant before contacting the connector. CRM writes default to disabled. In the authorized sandbox configuration only, set the strict boolean crm_write_enabled=true to enable the existing execution and Odoo adapter. This still requires scoped identities, current local approval and an approved connector binding. Set false and restart to disable dispatch. Email sending is independently disabled by default. To opt in for a controlled sandbox, set email_send_enabled=true and email_recipient_allowlist to the exact permitted addresses in the project-local connector file. A Graph connector, separate email approval, matching recipient, current source/deal and due-time eligibility are required. The worker sends once through the committed operation ledger; an uncertain outcome needs read-only reconciliation, never blind retry. The older send_enabled key remains rejected. Turn the setting off and restart to stop new dispatch; existing operations can still be observed when properly scoped and configured.

When a mapped test message shares the Inbox with unrelated mail, `POST /v1/ingest/graph/selected` accepts its explicit immutable Graph ID from the configured worker. It reads only that message, uses the same source/version checks as delta ingestion, and leaves the delta checkpoint unchanged. Unmapped IDs are rejected before a Graph request. This targeted path was used in the [combined Outlook acceptance](../evidence/phase-7-outlook-oauth-connected.json); routine delta polling retains its strict unmapped-message behavior.

The composition and denial tests remain regression coverage. For the connected Odoo read-back, Graph access, n8n execution and controlled-send evidence, use [the Phase 7 audit](COMPLETION-AUDIT.md); Graph send acceptance is not proof of recipient delivery.

For a fresh local install, supply only this project's authorized sandbox configuration and credential files. Begin with identity/read-only checks; remote state changes still require exact approval and current operator authorization.

## Personal Outlook account: project-owned OAuth

The preferred local setup uses a separate Microsoft app registration for Sales. In [Microsoft Entra app registrations](https://entra.microsoft.com/#view/Microsoft_AAD_RegisteredApps/ApplicationsListBlade), create a registration supporting **Personal Microsoft accounts**. In Authentication, enable **Allow public client flows** for device-code login. Add delegated Microsoft Graph permissions `User.Read`, `Mail.Read`, and `Mail.Send`. No client secret or redirect URI is needed for this public-client flow. Copy only the **Application (client) ID**; it is not a password. If your personal Microsoft account cannot access an Entra directory to register an app, tell the project owner rather than substituting an unrelated application's ID.

Run `.venv/Scripts/python.exe -m scripts.graph_auth_configure --client-id <Application-client-ID>`. This replaces only the Graph token-file reference in ignored `local/connectors.json`, preserves deal/Odoo mappings, and forces `email_send_enabled=false`. Then run `.venv/Scripts/python.exe -m scripts.graph_login`. The terminal prints a short device code and Microsoft sign-in URL. Complete consent using the intended Outlook account. The command checks `/me` and one message ID without sending or changing a checkpoint. The MSAL cache is encrypted with Windows DPAPI under ignored `local/secrets/graph-msal-cache.bin`. This workspace is inside OneDrive, so the encrypted cache may sync; do not share the `local` folder or copy the cache to another user's profile. The worker refreshes access silently and stops if login is required again. Run `.venv/Scripts/python.exe -m scripts.graph_readiness` for a later bounded check.

These setup commands do **not** enable dispatch. For a controlled send, separately set `email_send_enabled=true` and an exact `email_recipient_allowlist` in the local connector configuration, approve the email payload, and verify the queued job/due time. The previous Phase 8 release archive predates this OAuth implementation and needs a new validation before deployment. [Microsoft registration](https://learn.microsoft.com/en-us/graph/auth-register-app-v2), [MSAL device flow](https://learn.microsoft.com/en-us/entra/msal/python/getting-started/acquiring-tokens), and [encrypted cache](https://github.com/AzureAD/microsoft-authentication-extensions-for-python) describe the underlying platform behavior.

## Personal Outlook account: temporary Graph Explorer session

For a short interactive sandbox check, sign into [Graph Explorer](https://developer.microsoft.com/en-us/graph/graph-explorer) with the configured personal account. Consent to delegated User.Read and Mail.Read (the eventual ingestion reads message bodies). Copy the Access token tab's value into ignored local/secrets/graph-token, without a Bearer prefix, and select `token_file` instead of `oauth` in the Graph config. Do not put a Microsoft password or client secret there. This temporary developer session does not provide unattended refresh or application-owned OAuth registration.

Run `.venv/Scripts/python.exe -m scripts.graph_readiness`. The probe verifies /me against the configured mailbox before requesting at most one message ID through the adapter's /users addressing. It requests no body, follows no pagination, changes no database/checkpoint and prints only sanitized status/counts. Missing credentials fail before networking. Account aliases that do not match the returned profile fail closed and need explicit mapping verification. A passing probe proves only delegated identity and bounded read, not delta ingestion, send or end-to-end acceptance.

Sources checked 2026-10-10: [Graph Explorer features](https://learn.microsoft.com/en-us/graph/graph-explorer/graph-explorer-features), [personal-account User.Read](https://learn.microsoft.com/en-us/graph/api/user-get?view=graph-rest-1.0), [personal-account message delta permissions](https://learn.microsoft.com/en-us/graph/api/message-delta?view=graph-rest-1.0).

## Connected-lab model budget

For the accepted OpenAI profile set process variables OPENAI_MODEL=gpt-5.6-luna, OPENAI_REASONING_EFFORT=low, SALES_MODEL_ENABLED=true, SALES_MODEL_CALL_LIMIT=1 and SALES_MODEL_BUDGET_PATH=local/phase-6/budget.sqlite. Keep the API key in the existing project .env. The optional budget path must resolve inside this project's local directory; use the existing USD1 ledger so restarts do not reset its ceiling. The wrapper accepts only this priced profile, reserves before network access, limits input bytes/output allowance, and retains reservations when usage is unknown. It does not retry requests. Leave model execution disabled outside the bounded session.

Pricing rechecked 2026-10-10 against [official model documentation](https://developers.openai.com/api/docs/models/gpt-5.6-luna): USD0.20/M input and USD1.20/M output; reservations retain the conservative USD0.25/M input/cache-write rate used by Phase6. Budget reservations are conservative commitments, not billed cost.

## Operator review of n8n proposals

An operator scoped to the proposal deal may attach the approved connector binding to a worker-owned proposal only while its exact persisted worker job is awaiting approval. This grants no ownership transfer, local approval or execution. Other proposals keep owner-only binding. Delegation is checked again after remote validation; stale or changed jobs fail closed. The separate approver still approves the exact local payload before the worker executes. Operators use their own session in the existing binding form.
